# 项目规则

## 公告更新规则（updateLogs.ts）

### 核心原则

**公告 = 用户看到的版本变化，不是开发过程记录。**

### 发布时机

- 仅当版本为 release candidate（可发布）时，才生成用户公告
- 禁止每完成一个开发阶段就发布公告
- 禁止按时间（按天）发布公告

### 发布前置条件

公告内容必须满足以下全部条件才能写入：

1. `tsc --noEmit` 通过
2. `vite build` 通过
3. 全部测试通过
4. 人工验收通过（如存在）

### 公告内容边界

**允许（用户可感知）**：
- 新增功能（UI / 行为变化）
- 功能改进
- 交互变化
- 稳定性提升（仅用户感知层）

**禁止（必须过滤）**：
- hook / context / orchestrator / cache / trace / slice 等架构术语
- 测试新增与调整
- 文件拆分 / 重构说明
- 任何用户无法感知的实现细节

### 公告结构标准

每个 release 公告必须为：

- version（语义版本号）
- date（发布日期）
- title（用户可理解的一句话）
- 3~6 条 items（用户可感知变化，用用户语言描述）

### 两种日志系统

| 日志类型 | 文件 | 受众 | 更新频率 | 内容 |
|---------|------|------|---------|------|
| 开发日志 | `src/data/internalChangelog.ts` | 开发者 | 每阶段可更新 | 技术细节 |
| 用户公告 | `src/data/updateLogs.ts` | 用户 | 仅 release 时 | 用户可感知变化 |

### 发布流程

1. 功能开发完成
2. internal changelog 汇总阶段变化
3. 测试全部通过
4. 人工验收通过
5. 合并生成 release changelog（用户公告）
6. 提交 + 部署 + 发布公告

### 其他规则

- 每个版本公告一旦创建就是不可变的，禁止修改旧版本公告内容
- 版本号唯一，不可重复
- 一个版本 = 一次清晰认知，不碎片化
